# Решения проекта AI SMM Manager

Документ фиксирует только **принятые** решения. Изменение — отдельной записью в конце с датой и причиной.
Спорные варианты сюда не попадают: они живут в обсуждении, пока не выбраны.

## 1. Продукт

| Что | Решение | Дата |
|---|---|---|
| Формат | Desktop, local-first, PySide6 | принято |
| Пользователь | Один SMM-специалист / фрилансер, не агентство | принято |
| Клиенты | Казахстан; языки задаются бренд-профилем (RU или RU+KZ) | принято |
| Автономность | Рутина выполняется сама; подтверждение перед публикацией, удалением и тратами | принято |
| Публикации | В последнюю очередь: сначала движок создания и обработки | принято |

## 2. База кода

| Что | Решение |
|---|---|
| Основа | Рабочая модульная версия (`AI_SMM_Work_Architecture_A75`) |
| Архив A75 на GitHub | Источник проверенных узлов, не база: переносим media-ingest и publication-schema по мере надобности |
| Оболочка | Три панели: постоянная левая навигация, центральный рабочий стол, сворачиваемая AI-панель справа |
| Вид «Публикаций» | Утверждён по макету: пять нумерованных зон с цветными рамками |

## 3. Стек и модели

| Что | Решение |
|---|---|
| Хранение | SQLite на проект + общая база клиентов; бэкап при каждом запуске; токены шифруются |
| Локальные модели | Qwen3-8B-Instruct Q4_K_M — планирование и диалог; Qwen3-4B — редактор; bge-m3 — база знаний |
| Облако | Только финальные тексты, эскалация и KZ-контент; бюджет $30/мес, счётчик и стоп в интерфейсе |
| Медиа | Только обработка: кадрирование, цвет, сжатие, обложки, позже субтитры. Без генерации картинок |
| Роутинг | 4 слоя: правила → локальная модель с confidence → облачная эскалация → модель-редактор |

## 4. Этапы

- A (шаги 0–4): данные, каркас, ядро AI, цепочка стратегия → план → календарь → задачи.
- B: медиа — обработка фото, реальные превью, экспорт пакета.
- C: перенос из архива — аналитика, планы и схемы, материалы; видео и субтитры.
- D: Instagram (Graph API + публичный хостинг медиа).

**Приёмка этапа A:** новый клиент с нуля до 10 готовых постов в календаре за 30 минут, без правок в коде.

### 5.4 Канонические значения

| Поле | Значения | Старые значения → новое |
|---|---|---|
| `media.zone` | `sources`, `references`, `ready` | по исходному списку |
| `media.status` | `pending`, `approved`, `rejected`, NULL | NULL для `sources`/`references` |
| `content_plan.format` | `post`, `reels`, `stories`, `carousel`, `video` | `Пост`/`Post` → `post`, остальные по смыслу |
| `content_plan.status` | `draft`, `planned`, `in_progress`, `approved`, `published` | `Черновик`/`Draft`→`draft`, `Запланировано`/`Planned`→`planned`, `В работе`→`in_progress`, `Одобрено`→`approved` |
| `shooting_tasks.status` | `draft`, `planned`, `shot`, `editing`, `done`, `cancelled` | `Черновик`→`draft`, `Снято`→`shot` |

Даты — ISO `YYYY-MM-DD` в базе, `ДД.ММ.ГГГГ` только в интерфейсе. Время — `HH:MM`.
Деньги — `budget_amount` целым числом + `budget_currency` (`KZT`, `RUB`); строка «5000 ₽» разбирается при миграции.
Идентификаторы: старые (`cp_001`, `st_001`, `ev_001`, `src_001`, `ref_001`, `ready_001`) сохраняются как есть, чтобы не рвать связи; новые — `<префикс>_<6 hex>`.
Связи nullable, при удалении цели — `ON DELETE SET NULL`, кроме `publication_items.media_id` (`ON DELETE CASCADE`).

### 5.8 Журнал и откат

- Каждая запись инструмента — одна строка `actions_log` с `effect` (что изменено) и `undo` (обратная операция).
- Откат — обратная операция по `undo`, а не восстановление всей базы. Откат сам пишет строку в журнал.
- Файлы не удаляются: при «удалении» медиа переезжает в `media/quarantine/<project_id>/`, запись помечается, откат возвращает файл.
- `ai_runs` хранит расход отдельно от `ai_usage` в общей базе: суммарный счётчик бюджета считается по `app.db`.
- Журнал хранится 90 дней, затем чистится, кроме записей с `status='undone'`.

| 21.11.2026 | Версия стратегии считается как max(`1.N`) + 1, а не по длине `strategy_versions` | После откатов и удалённых записей длина списка давала повтор версии: 1.3 → 1.1 |

### 5.9 Метрики публикаций

Появляются на шаге 6а. До подключения Instagram API (этап C) цифры вводит пользователь руками.
Одна запись — одна позиция плана; повторный ввод перезаписывает значения, истории замеров нет.

| Поле | Тип | Откуда |
|---|---|---|
| `id` | TEXT PK | генерирует `add_record` |
| `plan_id` | TEXT | id позиции `content_plan`; метрики без позиции не существует |
| `reach` | INTEGER | охват, вводит пользователь |
| `likes` | INTEGER | лайки |
| `comments` | INTEGER | комментарии |
| `saves` | INTEGER | сохранения |
| `measured_at` | TEXT (ISO) | дата замера, необязательна |

Вовлечённость (ER) не хранится: считается на чтении как
`(likes + comments + saves) / reach × 100`, поэтому не может разъехаться с цифрами.
Пустая ячейка в таблице — это ноль, а не «не трогать»: иначе очищенное значение
возвращалось бы после перезагрузки.

### 5.10 Выгрузка PDF (шаг 6б)

Два документа, оба A4 книжно, кириллица из TTF-шрифта системы.

| Документ | Что внутри | Имя файла |
|---|---|---|
| План публикаций (`kind=plan`) | шапка: проект, дата выгрузки, число позиций; таблица: дата, тема, рубрика, формат, статус | `<ГГГГММДД-ЧЧММСС>-plan.pdf` |
| Стратегия (`kind=strategy`) | шапка: проект, версия, число блоков; блоки текстом; таблица KPI (метрика / сейчас / цель / срок) | `<ГГГГММДД-ЧЧММСС>-strategy.pdf` |

- Один инструмент `export_pdf(kind, dest)`: файл в выбранную папку, без выбора — в `<проект>/exports` (как пакет публикаций).
- Откат — `delete_file`: удаляется только созданный файл.
- Пустой план или пустая стратегия не выгружаются («выгружать нечего»), в журнал ничего не пишется — как у проверок без изменений.
- Библиотека — `fpdf2` (добавлена в `requirements.txt`); reportlab остаётся только фолбэком для старого экспорта ТЗ.
- Шрифт ищется в `FONT_CANDIDATES`; первым идёт `assets/DejaVuSans.ttf` проекта. Нет шрифта — сообщение, а не PDF с квадратами.
- Раздел называется «Планы и схемы», но схемы не рисует: выгружает ровно то, что уже есть в данных. Рисовать диаграммы из плана — отдельная задача, своих данных у неё нет.

### 5.11 Материалы (шаг 6в)

Пять папок фиксированы кодом (буфер, документы, референсы, шаблоны, архив) — это структура проекта,
а не пользовательские папки. Файлы лежат в `<проект>/materials/<папка>/`; в `other_files` добавлена
колонка `path` (для старых баз — `_ensure_columns`), а `id` теперь отдаётся наружу вместе с записью.

- `import_materials(paths, folder)`: копирует файлы в папку проекта (имя не затирается — `_1`, `_2`),
  добавляет записи с типом по расширению, размером, датой и пустыми тегами; откат — `restore_sections`
  возвращает список и удаляет скопированные файлы, исходники пользователя не трогаются.
- `delete_material(item_id)`: убирает только запись, файл остаётся на диске; откат возвращает запись.
  Карантина, как у медиа, здесь нет: материал — это документ, а перемещать чужие файлы без спроса нельзя.
- Раздел в навигации переименован в «Материалы» (был «Прочие материалы»): загрузка через диалог,
  поиск по имени и тегам, фильтр по типу, открытие системным просмотрщиком, предпросмотр изображений
  и удаление записи. Все изменения — через ядро, журнал и откат общие.

### 5.12 Видео (шаг C1)

Готовый `video_processor.py` подключён к ядру: `get_video_info` (ffprobe) и `export_for_platform` (ffmpeg).

- Инструмент `process_video(media_ids, platform)`: площадки из `PLATFORM_SETTINGS` — Reels 9:16, пост 1:1,
  TikTok, Shorts, YouTube 16:9. Готовый файл — `<имя исходника>_<reels|post|tiktok|shorts|youtube>.mp4`
  в `media/images`, при повторе перезаписывается (как `<имя>_web` у фото).
- Исходник ищется по `source_path` → `path` → файл с тем же именем в `media/images`, только среди видео-расширений.
- Запись получает `source_path` (исходник), `path` на готовый файл, `size` = фактические `ШxВ` из `get_video_info`,
  `processed` = площадка. Обработка считается от исходника, а не от прошлого готового файла.
- Откат — `restore_sections`: записи возвращаются, созданные файлы удаляются, исходник не трогается.
- Нет ffmpeg (или ffprobe) — честное «нужен ffmpeg» без записи в журнал: файла нет, менять нечего.
- Подгонка кадра — `scale` + `pad` (чёрные поля), без обрезки по центру: обрезка меняет кадр, это отдельное
  решение, а не следствие подключения.
- Кадр-превью видео (шаг 5) остаётся как был: он снимает кадр с записи, а не с готового файла.
- Роутер видео пока не маршрутизирует — из чата нечем выбрать конкретное видео; инструмент вызывается кнопкой
  в «Публикациях». Выбор видео из чата — следующий подшаг, вместе с субтитрами.
- В `get_video_info` `eval(r_frame_rate)` заменён разбором `num/den`: `eval` по выводу ffprobe — исполнение
  внешних данных.

### 5.13 Субтитры (шаг C2)

- `make_subtitles(media_ids, language="ru", burn=True)`: звук → `extract_audio` (wav 16 кГц моно, временный файл в `/tmp`) → `transcribe` → `.srt` в `<проект>/subtitles/<имя>.srt` (UTF-8 BOM — так его ждёт ffmpeg) → при `burn` готовое `<имя>_subs.mp4` в `media/images`.
- Источник — исходник (`source_path` → `path`), как у `process_video`; повтор перезаписывает `.srt` и `_subs.mp4`, а не плодит копии.
- Откат — `restore_sections`: записи возвращаются, созданные `.srt` и `.mp4` удаляются, исходник не трогается.
- `burn=False` — только `.srt`, запись не меняется (откат удаляет файл).
- Whisper — **опциональная** зависимость и в `requirements.txt` не входит (тянет torch): нет его или речь не распозналась — отчёт «нужен Whisper» без записи в журнал. Облачное распознавание не включаем автоматически: расход бюджета должен быть решением пользователя, а не следствием кнопки.
- VRAM 8 ГБ: Whisper и локальная LLM вместе не живут. В C2 модель не выгружается автоматически (это Ollama `keep_alive`), но риск записан и проверяется на машине пользователя.
- Язык — `ru` по умолчанию; KZ-распознавание остаётся облачным сценарием и в C2 не включается.
- В базу добавлена колонка `media.source_path` (для старых баз — `_ensure_columns`): без неё после перезапуска субтитры и повторная обработка считались бы с уже сжатого `_reels`/`_web` файла.
- Повторная обработка видео считается от имени без суффикса площадки (`_video_stem`): запись без `source_path`, указывающая на `clip_reels.mp4`, даёт `clip_reels.mp4`, а не `clip_reels_reels.mp4`.

### 5.14 Вид для видео (шаг C3)

- В `media` добавлена колонка `processed` (JSON-список): инструменты пишут туда, что сделали (`process_video` — площадку, `make_subtitles` — `subtitles`). Без хранения статус терялся после перезапуска, и «до/после» нечего было бы показать.
- Подписи — `PROCESSED_LABELS` в «Публикациях»: `🎬 Reels`, `🎬 Post`, `🎬 TikTok`, `🎬 Shorts`, `🎬 YouTube`, `💬 Субтитры`. Карточка в медиатеке и панель просмотра показывают их рядом со статусом.
- «До / после» — отдельный `VideoCompareDialog`: два кадра (исходник и готовое), имя файла, размер и длительность. Кадры берутся тем же `_pixmap_for`, что и у фото; длительность — через `get_video_info` (ffprobe), без ffmpeg — «длительность неизвестна», а не выдуманное число.
- Кнопка «🎬 До / после (видео)» стоит в просмотре рядом с «Сравнить с исходником»: фото-диалог сравнивает пиксели кадра, видео нужен кадр плюс длительность. Нет `source_path` — сообщение, как у фото.
- Сравнение только читает: ни файлов, ни базы не меняет, отката не требует.

### 5.15 Файлы из чата для видео и субтитров (шаг C4)

- Накопление статусов: `processed` только дописывается (`_remember`) — повторная подготовка под ту же площадку и субтитры после видео не стирают предыдущие отметки и не плодят дубли. Фото — исключение: `batch_photo` пишет последний рецепт (`crop`/`color`/`compress`), это не история, а что именно сделано с файлом.
- `process_video` и `make_subtitles` принимают `paths` — пути из текста чата. Путь разрешается в запись по `path`/`source_path`; файл не из проекта копируется в `media/images` (`_add_media_record`), оригинал остаётся в `source_path`, поэтому тот же путь второй раз не создаёт копию.
- Копирование — до обработки, но только после проверки ffmpeg: без него файлы в проект не тянутся.
- Откат после обработки по пути: возвращаются записи, удаляются готовые файлы; импортированная копия исходника остаётся в медиатеке (это исходник, а не результат).
- Маршрут из чата: правило срабатывает только если в тексте есть и слово площадки/субтитров, и путь к видеофайлу (`*.mp4|mov|mkv|avi|webm|m4v`). Нет пути — уточняющий вопрос, а не запуск по пустому списку: инструмент из чата без файла не угадывает материал.
- В «Публикациях» те же кнопки работают без выделения: если видео не выбрано, открывается выбор файла на диске, и запуск идёт через `paths`.
- id записей из чата — та же схема, что у импорта; никаких новых таблиц не нужно.

### 5.16 Пакет под Instagram (шаг C5)

- Прямая публикация через Graph API сейчас невозможна: Instagram забирает медиа по публичному URL, а приложение local-first таких URL не отдаёт; нужны ещё бизнес-аккаунт и токен. Поэтому C5 — пакет для ручной загрузки, а постинг остаётся отдельным шагом D («Graph API + публичный хостинг медиа», раздел 4).
- `instagram_pack(dest="")` собирает `<папка>/ГГГГММДД-ЧЧММСС/`:
  - `media/` — копии одобренных материалов (`status = approved`), имя `<дата>_<слаг>.<ext>`;
  - `captions.txt` — дата, тема, подпись и хэштеги по позициям плана;
  - `manifest.csv` — файл; тип; формат; размер; операции из `processed`;
  - `problems.txt` — чего не хватает: нет файла, нет подписи, нет хэштегов.
- Замечания не блокируют сборку: неполный пакет тоже нужен, а `problems.txt` говорит, что дописать.
- Без `dest` — `<проект>/instagram/…`, с `dest` — подпапка в выбранной папке; откат `delete_folder` удаляет только созданную подпапку.
- Копируются файлы, а не ссылки: загрузка с телефона или из веба требует файлов; исходники не меняются.
- Подпись привязана к файлу (`_pair_captions`): сначала позиция плана с тем же `media_id`, затем совпадение дат, затем остатки — в порядке плана. Каждая пара попадает в `captions/<имя файла>.txt`, блок в `captions.txt` начинается с `=== <имя файла> ===`, а в `manifest.csv` есть колонка «подпись» (да/нет). Несвязанные позиции и файлы — в `problems.txt`, а не отдельным списком без якорей.
- Кнопка «📸 Пакет в Instagram» в шапке «Публикаций»; правило чата — «пакет/публикация» + «инстаграм».
- Подписи операций в карточке: `crop`/`color`/`compress` — «Кадр»/«Цвет»/«Сжатие»; незнакомые ключи в интерфейсе не показываются сырым текстом (`_processed_marks`).
- Хостинг медиа для реальной публикации — открытый вопрос (5.17): пока его нет, Graph API не подключаем.

### 5.19 Токен Instagram и проверка доступа (шаг D3)

- Хранение — таблица `instagram_token` (одна строка, `id = 1`) в **общей** `data/app.db`, а не в базе проекта и не в `settings.json`: токен относится к аккаунту, а не к клиенту, и не должен уезжать с бэкапом проекта.
- Шифрование — `cryptography` (Fernet, AES-CBC + HMAC). Зависимость добавлена в `requirements.txt`; своего шифра в проекте не пишем.
- Ключ: `AI_SMM_TOKEN_KEY` из окружения; если его нет — `data/.token_key`, создаётся при первом сохранении с правами `0600` и исключён из git. Потеря ключа = токен нужно ввести заново (это лучше, чем хранить ключ рядом с шифртекстом открыто).
- Токен **никогда не передаётся аргументом инструмента**: `actions_log` хранит аргументы, и значение попало бы в журнал. Ввод — только в «Настройках» (поле с `EchoMode.Password`), запись идёт напрямую в `TokenStore`; AI получает только `instagram_status()` без аргументов.
- В интерфейсе и отчётах — только `mask()` (последние 4 символа). Текст ошибок Graph API и `requests` проходит через `_scrub()`: адрес `/me?access_token=…` из исключения иначе вынес бы токен в сообщение и в журнал.
- Проверка доступа — read-only `GET https://graph.instagram.com/me?fields=id,username,account_type`, без публикации: 200 + `BUSINESS`/`CREATOR` = готово; `PERSONAL` = «нужен Business или Creator»; код ошибки 190 = «токен просрочен или отозван». Сеть недоступна — честное «сеть недоступна».
- `instagram_status()` пишет строку в журнал только при успехе (`undo = noop`, как у `validate_plan`), потому что это отчёт, а не изменение; неуспех — просто ответ без записи.
- Правило чата: «проверь доступ (к инстаграму)» → `instagram_status`.

- **App Review и Advanced Access:** разрешения `instagram_business_basic` и `instagram_business_content_publish` (или `instagram_basic` + `instagram_content_publish`) требуют заявки на проверку. Без Advanced Access работает только доступ разработчиков приложения. Это действие пользователя в кабинете Meta, кодом его не закрыть.

### 5.18 Публикация в Instagram через Graph API (шаг D, D1)

Факты из документации Meta (раздел «Content Publishing»):
- Meta скачивает медиа сама (`We cURL media used in publishing attempts`), поэтому файл должен лежать на **публично доступном сервере с HTTPS без авторизации** в момент публикации.
- Публикуется только **профессиональный аккаунт** (Business или Creator). Путь «Instagram API with Instagram Login» (хост `graph.instagram.com`, Business Login for Instagram) не требует связанной Facebook Page; путь «с Facebook Login» требует Page.
- Лимиты: контейнер живёт **24 часа**, за 24 часа — не более **400 контейнеров** и **50 публикаций** на аккаунт; если подключённая Page требует Page Publishing Authorization (PPA), публикация падает без её завершения.

Решение:
- **Хостинг — Cloudinary (основной).** Бесплатный тариф без карты, загрузка одним POST на `api.cloudinary.com/v1_1/<cloud>/image/upload` (без SDK, только `requests`), отдача — `res.cloudinary.com/<cloud>/image/upload/…` без логина. Buffer и официальные туториалы рекомендуют именно его для этого кейса: прямой URL получается сразу после загрузки. Удаление — тем же API с подписью, поэтому откат D2 возможен.
  - Резерв — Cloudflare R2: бесплатные 10 ГБ и нулевой исходящий трафик, но публичный доступ требует отдельной настройки (публичный бакет или свой домен), а загрузка идёт по S3-протоколу. Переход не меняет D3/D4.
  - Не подходят: GitHub Pages (запрещено для бизнеса, 1 ГБ на сайт), Vercel Hobby (только некоммерческое использование), анонимные файлообменники (нет гарантий срока жизни и удаления — а откат нужен).
- **Токен — долгоживущий токен пользователя Instagram** (не Page-токен и не короткий на час). Хранится **не** в `settings.json` и **не** в базе проекта: отдельная таблица в общей `data/app.db`, значение **шифруется** (согласно таблице стека, раздел 3). Ключ шифрования — вне репозитория (переменная окружения или системное хранилище ОС). В интерфейсе показываются только последние 4 символа; токен не попадает в журнал, логи и `actions_log`.
  - Доступ разработчика в приложении Meta нужен для проверки; Advanced Access запрашивается отдельно (см. 5.17).
- **Проверка бизнес-аккаунта (D3, read-only, без публикации):**
  1. `GET /me?fields=id,username,account_type&access_token=…` — аккаунт отвечает, `account_type` равен `BUSINESS` или `CREATOR`;
  2. проверка, что токен живёт (ошибка `OAuthException` с кодом 190 означает протухший или отозванный токен);
  3. права `instagram_business_basic`/`instagram_business_content_publish` видны в ответе Graph API Explorer или по попытке одного read-only запроса с ними.
  По этим трём пунктам D3 считает доступ готовым; PPA проверяется вручную в Meta Business Suite, если публикация упадёт с соответствующей ошибкой.
- **Публикация (D4):** только после D2+D3, с обязательным подтверждением (правило ядра), dry-run по умолчанию; каждый вызов пишется в журнал, откат удаляет загруженный файл и помечает публикацию как отменённую локально (саму опубликованную запись из Instagram приложение не удаляет — это ограничение API).

Открытые вопросы, которые остаются после D1:
- Действительно ли Cloudinary отдаёт наши видео без трансформации и не режет качество — проверяется на D2 живым файлом.
- Сколько живёт долгоживущий токен на практике и как часто его обновлять — измеряется на D3.

### 5.20 Публикация в Instagram (шаг D, D4)

- **Порядок вызовов Graph API** (`graph.instagram.com`, Instagram API with Instagram Login): проверка
  `GET /{ig-user-id}/content_publishing_limit` (только чтение) → `POST /{ig-user-id}/media` с `image_url`
  или `video_url` и `media_type` (`IMAGE` для фото, `REELS` для видео) → для видео опрос
  `GET /{container-id}?fields=status_code` до `FINISHED` (короткий лимит ожидания, без бесконечного цикла) →
  `POST /{ig-user-id}/media_publish` с `creation_id`.
- **Инструмент `instagram_publish(media_id, dry_run=True, again=False)`:** по умолчанию только проверка —
  печатает подпись, публичный URL, аккаунт и остаток лимита, сети на запись не делает. Реальная публикация
  требует `dry_run=False`; такой вызов идёт через подтверждение (`needs_confirmation`).
- **Без URL — не публикуем:** материал без `remote_url` (не выложен через `host_media`) отказывается с подсказкой.
- **Дубли:** если у материала уже есть `published_id`, повторная публикация отказывается, пока не придёт
  `again=True`, который тоже идёт через подтверждение.
- **Лимиты:** перед публикацией читаем `content_publishing_limit`; если квота исчерпана (50 публикаций в 24 ч) —
  отказ без записи. Контейнер живёт 24 ч: при таймауте опроса честно говорим, что контейнер не опубликован.
- **Откат:** API не удаляет пост Instagram. Откат возвращает запись в локальную базу (убирает
  `published_id`, отметку `published`) и прямо говорит, что пост в Instagram остался — удалить его надо вручную.
- **Журнал:** запись только при реальной публикации (`dry_run=False`) с итогом `published_id`. Проверка и
  dry-run журнал не пишут, токен не попадает ни в аргументы, ни в ответ (`_scrub`).
- **Модель:** Claude Haiku 4.5 (по запросу пользователя), запасной вариант — DeepSeek V4.1 Flash Next.
- **Не проверено вживую:** настоящая публикация (в VM нет токена Meta, Cloudinary и сети до Graph API).

### 5.21 Чеклист живой проверки публикации в Instagram (шаг D4, для пользователя)

Выполняется на вашем компьютере с настоящим аккаунтом. В этой среде живой проверки не было.

1. **Аккаунт:** Instagram — Business или Creator, связан со страницей Facebook; в настройках токен выдан с правами публикации.
2. **Токен:** вписан в «Настройках» (шифруется в `data/app.db`); в «Настройках» видна маска, а не значение.
3. **Проверка доступа:** инструмент проверки показывает `@ваш_аккаунт` и тип профессиональный. Если токен просрочен — появится «получи новый».
4. **Публичный URL:** выбранный материал выложен через `host_media` (Cloudinary; R2 пока не реализован), ссылка открывается в браузере без входа.
5. **Dry-run (по умолчанию):** `instagram_publish` без подтверждения показывает «Проверка прошла, публикация не запущена», осталось публикаций N из 50. В Instagram ничего не появилось.
6. **Лимит:** в сообщении видно осталось публикаций; при 0 публикация не запускается.
7. **Фото (IMAGE):** реальная публикация с подтверждением — пост появился в ленте, в журнале есть запись с `published_id`.
8. **Видео (REELS):** файл дождался статуса FINISHED (до 60 с); если не успел — сообщение «повторите позже», пост не создан, дублей нет.
9. **Повтор:** второй запуск без `again` блокируется сообщением «уже опубликован»; с подтверждением — публикуется ещё раз (это ожидаемо).
10. **Откат:** `undo` снимает локальную отметку `published_id`; пост в Instagram удаляется вручную в приложении Instagram.
11. **Утечки:** в журнале, в логах и в выводе инструмента нет строки токена (поиск по значению токена пустой).
12. **Ошибка сети или токена:** понятное сообщение без токена, запись материала не меняется.

Не проверено в VM: все пункты, кроме проверок на фейковом Graph API (`d4_test`, 16/16).

### 5.30 Замеры в acceptance_live без загрузки модели
Перед стартом таймеров раннер делает короткий прогрев (8 токенов) и печатает его время отдельной строкой. Живые прогоны показали разброс 90.6 с против 10.6 с на первой подписи, то есть первый ответ после простоя включал загрузку весов.

### 5.31 Подтверждение перед публикацией, а не перед проверкой
`needs_confirmation` у `instagram_publish` был перевёрнут: вопрос «да/нет» задавался при `dry_run=1` и не задавался при `dry_run=0`. Теперь подтверждение требуется только тогда, когда вызов может реально опубликовать (`dry_run` в `("0","false","нет")`); dry-run идёт без вопроса. Повтор (`again`) без `dry_run=0` ничего не публикует, поэтому отдельного условия не нужно — реальный повтор спрашивается тем же правилом.

### 5.32 Публикация из чата идёт через модель, не через правило
`_rules` знает «пакет в инстаграм», но не саму публикацию: «опубликуй материал m1» не ловится ни одним правилом и уходит в слой 2 (модель), которая возвращает `instagram_publish` с `media_id`. `dry_run` модель не подставляет — значение по умолчанию «1» даёт сам инструмент, поэтому dry-run остаётся безопасным даже при молчаливой модели. Гейт подтверждения срабатывает уже после маршрута, в `handle()`.

Следствие: надёжность фразы в чате зависит от того, вернёт ли локальная модель правильный JSON. Отдельное правило для «опубликуй» сделало бы путь детерминированным; пока его нет.

### 5.33 Публикация из чата ловится правилом, а не моделью
Правило в `_rules`: глагол «опублику…/запости/publish» + id материала → `instagram_publish`. Id берётся после слова «материал/медиа/файл/media», иначе ищется известный id материала в тексте (границы слова). `dry_run` правило не ставит — остаётся значение по умолчанию «1»; явные «без проверки», «по-настоящему», «вживую», «действительно», `dry_run=0` дают `dry_run="0"`. Если id не найден, правило молчит и работает прежний путь через модель. «Подготовь публикацию в инстаграм» остаётся `instagram_pack`.

### 5.34 Правило публикации не угадывает материал
Кандидат в id принимается только если он совпадает с id существующего материала (без учёта регистра); иначе ищется известный id в тексте по границам слова. Если ничего не нашлось, инструмент не вызывается — правило отдаёт уточнение со списком доступных материалов («Какой материал опубликовать? Доступные: …», до 10 позиций), а в пустом проекте подсказывает импорт. Так «опубликуй материал 3 поста» не превращается в media_id «3» и не даёт ложный отказ «материал не найден».

### 5.35 Тесты печатают в консоль Windows без падений
Стрелка «→» не входит в cp1251, и печать падала с `UnicodeEncodeError` на машине владельца. В тестах публикации теперь только символы cp1251 (`->` вместо стрелки), а раннер ставит дочерним процессам `PYTHONIOENCODING=<кодировка консоли>:replace`, чтобы любая чужая типографика не валила прогон. Раннер также проверяет `cryptography` и подсказывает запуск через venv или `pip install -r requirements.txt`.

### 5.36 Проверки живут в репозитории и идут одной командой
Все проверки — в `work/tests/`, запуск: `python work/tests/run_tests.py` (при `--publish` только публикация, именем файла — одна проверка). Каждый тест считает пути от себя: `APP` — код приложения, `PROJECT` — корень репозитория, `WORK` — свой временный каталог на прогон, поэтому `/tmp` не нужен ни на Windows, ни на Linux. Раннер ставит `QT_QPA_PLATFORM=offscreen`, кодировку консоли с `errors=replace` и подсказывает venv, если не хватает `cryptography`.

### 5.37 Тесты не оставляют мусора в папке медиа
`test_step7` и `test_step8` работают в реальном `media/images` приложения (кэш кадров `.thumbs` считается в `publications_section` от `MEDIA_DIR` при импорте, поэтому подмена `ai_core.MEDIA_IMAGES` его не переносит). Вместо временной папки они убирают за собой через `atexit`: файлы `t7_*`/`t8_*` удаляются и при падении проверки, пустой `.thumbs` удаляется. Заголовок теста объявляет `WORK` только там, где файл не заводит свой каталог.

### 5.38 Тесты убирают медиа через общий помощник, подсказка не врёт про venv
Копии импортированных файлов и результаты обработки приложение кладёт в `media/images`, поэтому тесты, которым нужна именно эта папка, регистрируют `cleanup_media(*шаблоны)` из `work/tests/_cleanup.py`: уборка выполняется на старте и по `atexit`, то есть и при падении проверки. Подсказка раннера про `cryptography` печатает путь к интерпретатору только если он существует (корневой `venv`, затем `.venv` приложения — как в `START.bat`), иначе предлагает `pip install -r requirements.txt`.

### 5.39 Заглушки внешних программ — подменой `subprocess`, а не файлами в PATH
Тесты, которым нужен ffmpeg, не создают исполняемые скрипты в PATH: на Windows `subprocess.run(["ffmpeg", ...])` ищет только `.exe`, а `#!/bin/sh` не запускается вовсе, поэтому брался установленный ffmpeg и падал на поддельном видео. Вместо этого `work/tests/_ffmpeg_fake.py` подменяет `subprocess` в самом модуле приложения: `patch_ffmpeg(module)`, `patch_ffmpeg(module, poster_source=png)`, `patch_ffmpeg(module, available=False)`. Подмена живёт до конца процесса теста, восстанавливать её не нужно. Шрифт для PDF-теста выбирается из списка существующих путей под Linux/Windows/macOS, а `FONT_CANDIDATES` после проверки «без шрифта» возвращается к исходному состоянию, а не к одному linux-пути.

### 5.40 Шрифт с кириллицей поставляется вместе с приложением
PDF-выгрузка не должна зависеть от системных шрифтов: `assets/DejaVuSans.ttf` лежит в репозитории первым кандидатом, рядом — `DejaVuSans.LICENSE.txt` (лицензия Bitstream Vera требует прикладывать текст разрешения). Системные пути (Arial/Tahoma на Windows, DejaVu на Linux, Helvetica на macOS) остаются запасными. Если шрифта нет вообще, сообщение называет папку `assets/` и способ указать свой TTF, а не только список имён шрифтов.

### 5.41 Подпись поста правится руками, а не только генерируется
Данные всегда позволяли менять `caption` через `edit_record`, но в GUI подпись была только для чтения: единственным способом её изменить была повторная генерация ИИ. Добавлен `PostDialog` в `content_plan_section`: поля плана и многострочная подпись с лимитом 400 (счётчик, блокировка сохранения за лимитом), кнопки «Сгенерировать» и «Копировать». Диалог открывается кнопкой «✎ Править» и сразу после «＋ Позиция». Сохранение идёт тем же журнальным `edit_record`, поэтому правку можно откатить, как любую другую операцию.

### 5.42 Удалённый раздел стратегии не стирает связь поста
`strategy_link` хранится как id раздела. Если раздел удалён, диалог поста добавляет в список пункт «<id> — раздел удалён» с тем же значением, показывает красное предупреждение и при сохранении пишет прежний id; в статусе появляется пометка «связь со стратегией … сохранена (раздел удалён)». Отвязка возможна только явным выбором «—», то есть молчаливой потери связи нет.

### 5.43 Медиа привязывается к позиции плана списком id
У позиции контент-плана появилось поле `media_ids` — список id из `media_ready`, пишется через тот же журнальный `edit_record`, поэтому откатывается вместе с остальными полями. В диалоге поста видно миниатюры прикреплённого (фото — превью, видео — кадр через `_pixmap_for`), «Прикрепить…» открывает выбор из готовых материалов с превью и отметками, клик по миниатюре убирает материал. Отдельного файла-копии не создаётся: связь через id, так что переименование или переобработка материала не рвёт привязку, а отсутствующий файл даёт пустую иконку вместо падения.

### 5.44 Чат AI не блокирует окно и не молчит
`ai_core.handle` уходит в модель и может идти десятки секунд (а на большой модели — минуты), поэтому в `AIPanel` он считается в `QThread` (`_ReplyWorker`), а не в UI-потоке. Пользователь сразу видит своё сообщение и плашку «⏳ Думаю… N с»; второй запрос, пока идёт первый, отклоняется с объяснением. Любой исход виден в чате: ответ, «Ошибка ядра AI: …» или «Ядро вернуло пустой ответ». Модель, которая не подключена, называется в уточнении прямо — вместо общего «Не понял задачу».

### 5.45 Локальная модель выбирается из установленных и грузится заранее
Для маршрутизации и текстов берём `qwen3:8b` (5.2 ГБ, влезает в 8 ГБ VRAM, нормальный русский). `AICore.ensure_local_model()` при подключении проекта: проверяет Ollama, при отсутствии настроенной модели берёт первую установленную из `LOCAL_MODEL_PREFERENCE = (qwen3:8b, qwen2.5:7b-instruct, gemma3:4b, llama3.1:8b)` и переключает провайдера, затем делает `warm_up` с `keep_alive=15m` — модель уже в памяти к первому вопросу. Если подходящей модели нет, сообщение содержит команду `ollama pull qwen3:8b` и ссылку на библиотеку; если Ollama не запущен — подсказку `ollama serve`. Скачивание автоматически не запускается: это гигабайты трафика, решение за владельцем.

### 5.46 Автоподмена модели фиксируется в настройках
Автоматический выбор модели не должен повторяться на каждом запуске: после подмены `local_model` записывается в `config/settings.json` через `Settings.set` + `save` (или в словарь настроек, если он передан словарём), а сообщение в чате сообщает, что выбор сохранён. Если записать не удалось, пользователь видит это и подсказку вписать модель вручную. Значение по умолчанию в `DEFAULTS` — `qwen3:8b`.

### 5.47 Локальная модель в настройках — список из Ollama, а не свободный ввод
Свободное поле давало рассинхрон: после автоподмены модели раздел показывал старое значение, а сохранение записывало его обратно и затирало выбор. Теперь это `QComboBox`, заполняемый `OllamaProvider.models()`: список реально скачанных моделей, кнопка «Обновить», сохранённая модель, которой нет в Ollama, показывается пунктом «<имя> — не установлена» и сохраняется своим именем. При открытии раздела `showEvent` подхватывает значение из настроек без сетевого запроса, поэтому автоподмена из чата сразу видна в поле. Сохранение берёт имя из данных пункта, а не текст с пометкой.

### 5.48 Менеджер — агент, а не парсер команд
Задача пользователя больше не обязана совпадать с шаблоном: `AIAgent` даёт модели состояние проекта и каталог инструментов и ведёт цикл до 6 шагов (`{action: tool|done|ask}`), выполняя каждый шаг через журнальный `_execute`. Правила остаются первым слоем для однозначных и опасных операций (публикация, журнал, откат, доступ, видео по путям) — они работают без модели и не тратят её вызовы. Публикация в Instagram агенту запрещена: инструменты публикации и хостинга исключены из его каталога, в ответе он говорит, что публикует человек. Инструменты подписей и ТЗ умеют работать по всем позициям сразу, поэтому одна задача доводится до результата, а не до первого шага.

### 5.49 Ответ модели разбирается терпимо, а не по одному шаблону
Шаг агента принимается в любом разумном виде: `tool`/`tool_name`/`name`/`action`, `args`/`arguments`/`params` (словарём или JSON-строкой), вложенный `step`, `function`/`tool_calls`, список из одного шага, JSON внутри текста или ```json-блока. Неразобранный ответ не останавливает работу: на первом шаге — фолбэк на прежний слой, дальше — подсказка в историю и следующий шаг; проза после сделанного шага считается ответом. Пустое `done` без единого действия отклоняется один раз, чтобы задача не закрывалась «Готово» без работы. Живой прогон вынесен в `--live`, чтобы реальная модель проверялась одной командой, а не вручную.

### 5.50 Выдуманный инструмент — это ошибка шага, а не «готово»
Ответ модели с несуществующим инструментом больше не может закрыть задачу. `normalize_agent_action` узнаёт в нём шаг (`kind=tool` с любым именем), даже если имени нет в реестре; `action=tool` без имени — тоже шаг, а не завершение. Агент возвращает модели ошибку с ближайшими по смыслу именами (`difflib.get_close_matches`) и требованием продолжить, а после `AGENT_UNKNOWN_LIMIT = 2` таких шагов честно останавливается: называет выдуманные имена, сколько действий успел сделать, и не пишет «Готово». Так же отсекаются инструменты из `AGENT_DENY`: модель узнаёт, что публикует человек, вместо молчаливого обрыва. Шаг агента идёт в Ollama с `format: "json"` (`OllamaProvider.chat(fmt=...)`), поэтому проза вокруг JSON появляется реже; `_agent_chat` передаёт параметр только тем провайдерам, у которых он есть в подписи, — облачный слой и тестовые двойники не ломаются.

### 5.51 После плана задача не закрывается «готово»
qwen3:8b создаёт контент-план и сразу говорит done — подписей и ТЗ нет. Поэтому «готово» после создания новых позиций плана проходит проверку готовности: `_plan_gaps(new_ids)` смотрит только на позиции, появившиеся в этой задаче, — есть ли у них `caption` и `shooting_task_id`. Если нет — модели один раз уходит точная подсказка («нет подписей и ТЗ — выполни write_captions, create_shooting_task»), и цикл продолжается; если она упирается в «готово» снова или доходит до лимита шагов, агент доводит цепочку сам теми же журнальными инструментами, вызывая их с `plan_id` каждой новой позиции, и честно пишет об этом: «Из N новых позиций: с подписью X, с ТЗ Y. Довёл до конца сам: …». Слова модели не теряются — её первый итог остаётся в начале ответа. Новые позиции определяются по разнице набора id плана до/после шага: старые посты с готовыми подписями и ТЗ не переписываются и не получают второе ТЗ, а валидация или вопрос по плану вообще не тянут за собой подписи. `create_strategy` теперь принимает блоки и строками («Название: текст»): на qwen3:8b он падал `AttributeError: 'str' object has no attribute 'get'`, и задача тратила все шаги на повторный вызов.

### 5.52 «Нужно N постов» — правило, а не надежда на модель
Формулировки «нужно/нужны/надо/хочу/сделай/создай/подготовь/добавь/дай + число + посты/публикации/позиции» обслуживает правило, а не агент: на живой модели такая фраза иногда не давала ни одного шага и падала в «Не понял задачу». Правило возвращает внутреннее решение `create_post_cycle` — не инструмент реестра и не шаг агента, поэтому каталог инструментов не меняется. `handle` перехватывает его до поиска в реестре (как `undo_last`/`show_journal`) и вызывает `_posts_cycle`: сначала `create_content_plan`, затем тот же `_finish_after_plan` по id, которые появились в этой задаче, — подписи и ТЗ пишутся с `plan_id` каждой новой позиции. Запросы со словом «контент-план» остаются за прежним правилом без доделки, чтобы не менять поведение старых формулировок. В итог идёт сводка инструмента без строки «Журнал: …», а успех называется только по тем инструментам, которые действительно записали изменение: при отсутствии модели ответ говорит «Дописать не смог» вместо «Довёл до конца».
