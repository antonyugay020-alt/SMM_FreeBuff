# Решения проекта AI SMM Manager

Документ фиксирует только **принятые** решения. Изменение — отдельной записью в конце с датой и причиной.
Спорные варианты сюда не попадают: они живут в обсуждении, пока не выбраны.

## 1. Продукт

| Что | Решение | Дата |
|---|---|---|
| Формат | Desktop, local-first, PySide6 | принято |
| Пользователь | Один SMM-специалист / фрилансер, не агентство | принято |
| Клиенты | Казахстан; языки задаются бренд-профилем (RU или RU+KZ) | принято |
| Автономность | Рутина выполняется сама; подтверждение перед публикацией, удалением и тратами | принято |
| Публикации | В последнюю очередь: сначала движок создания и обработки | принято |

## 2. База кода

| Что | Решение |
|---|---|
| Основа | Рабочая модульная версия (`AI_SMM_Work_Architecture_A75`) |
| Архив A75 на GitHub | Источник проверенных узлов, не база: переносим media-ingest и publication-schema по мере надобности |
| Оболочка | Три панели: постоянная левая навигация, центральный рабочий стол, сворачиваемая AI-панель справа |
| Вид «Публикаций» | Утверждён по макету: пять нумерованных зон с цветными рамками |

## 3. Стек и модели

| Что | Решение |
|---|---|
| Хранение | SQLite на проект + общая база клиентов; бэкап при каждом запуске; токены шифруются |
| Локальные модели | Qwen3-8B-Instruct Q4_K_M — планирование и диалог; Qwen3-4B — редактор; bge-m3 — база знаний |
| Облако | Только финальные тексты, эскалация и KZ-контент; бюджет $30/мес, счётчик и стоп в интерфейсе |
| Медиа | Только обработка: кадрирование, цвет, сжатие, обложки, позже субтитры. Без генерации картинок |
| Роутинг | 4 слоя: правила → локальная модель с confidence → облачная эскалация → модель-редактор |

## 4. Этапы

- A (шаги 0–4): данные, каркас, ядро AI, цепочка стратегия → план → календарь → задачи.
- B: медиа — обработка фото, реальные превью, экспорт пакета.
- C: перенос из архива — аналитика, планы и схемы, материалы; видео и субтитры.
- D: Instagram (Graph API + публичный хостинг медиа).

**Приёмка этапа A:** новый клиент с нуля до 10 готовых постов в календаре за 30 минут, без правок в коде.

### 5.4 Канонические значения

| Поле | Значения | Старые значения → новое |
|---|---|---|
| `media.zone` | `sources`, `references`, `ready` | по исходному списку |
| `media.status` | `pending`, `approved`, `rejected`, NULL | NULL для `sources`/`references` |
| `content_plan.format` | `post`, `reels`, `stories`, `carousel`, `video` | `Пост`/`Post` → `post`, остальные по смыслу |
| `content_plan.status` | `draft`, `planned`, `in_progress`, `approved`, `published` | `Черновик`/`Draft`→`draft`, `Запланировано`/`Planned`→`planned`, `В работе`→`in_progress`, `Одобрено`→`approved` |
| `shooting_tasks.status` | `draft`, `planned`, `shot`, `editing`, `done`, `cancelled` | `Черновик`→`draft`, `Снято`→`shot` |
| `calendar_events.type` | `publication`, `shooting`, `meeting`, `brand_event` | `Контент`→`publication` |
| `priority` | `low`, `medium`, `high` | `Низкий`→`low`, `Средний`→`medium`, `Высокий`→`high` |

Даты — ISO `YYYY-MM-DD` в базе, `ДД.ММ.ГГГГ` только в интерфейсе. Время — `HH:MM`.
Деньги — `budget_amount` целым числом + `budget_currency` (`KZT`, `RUB`); строка «5000 ₽» разбирается при миграции.
Идентификаторы: старые (`cp_001`, `st_001`, `ev_001`, `src_001`, `ref_001`, `ready_001`) сохраняются как есть, чтобы не рвать связи; новые — `<префикс>_<6 hex>`.
Связи nullable, при удалении цели — `ON DELETE SET NULL`, кроме `publication_items.media_id` (`ON DELETE CASCADE`).

### 5.8 Журнал и откат

- Каждая запись инструмента — одна строка `actions_log` с `effect` (что изменено) и `undo` (обратная операция).
- Откат — обратная операция по `undo`, а не восстановление всей базы. Откат сам пишет строку в журнал.
- Файлы не удаляются: при «удалении» медиа переезжает в `media/quarantine/<project_id>/`, запись помечается, откат возвращает файл.
- `ai_runs` хранит расход отдельно от `ai_usage` в общей базе: суммарный счётчик бюджета считается по `app.db`.
- Журнал хранится 90 дней, затем чистится, кроме записей с `status='undone'`.

| 21.11.2026 | Версия стратегии считается как max(`1.N`) + 1, а не по длине `strategy_versions` | После откатов и удалённых записей длина списка давала повтор версии: 1.3 → 1.1 |

### 5.9 Метрики публикаций

Появляются на шаге 6а. До подключения Instagram API (этап C) цифры вводит пользователь руками.
Одна запись — одна позиция плана; повторный ввод перезаписывает значения, истории замеров нет.

| Поле | Тип | Откуда |
|---|---|---|
| `id` | TEXT PK | генерирует `add_record` |
| `plan_id` | TEXT | id позиции `content_plan`; метрики без позиции не существует |
| `reach` | INTEGER | охват, вводит пользователь |
| `likes` | INTEGER | лайки |
| `comments` | INTEGER | комментарии |
| `saves` | INTEGER | сохранения |
| `measured_at` | TEXT (ISO) | дата замера, необязательна |

Вовлечённость (ER) не хранится: считается на чтении как
`(likes + comments + saves) / reach × 100`, поэтому не может разъехаться с цифрами.
Пустая ячейка в таблице — это ноль, а не «не трогать»: иначе очищенное значение
возвращалось бы после перезагрузки.

### 5.10 Выгрузка PDF (шаг 6б)

Два документа, оба A4 книжно, кириллица из TTF-шрифта системы.

| Документ | Что внутри | Имя файла |
|---|---|---|
| План публикаций (`kind=plan`) | шапка: проект, дата выгрузки, число позиций; таблица: дата, тема, рубрика, формат, статус | `<ГГГГММДД-ЧЧММСС>-plan.pdf` |
| Стратегия (`kind=strategy`) | шапка: проект, версия, число блоков; блоки текстом; таблица KPI (метрика / сейчас / цель / срок) | `<ГГГГММДД-ЧЧММСС>-strategy.pdf` |

- Один инструмент `export_pdf(kind, dest)`: файл в выбранную папку, без выбора — в `<проект>/exports` (как пакет публикаций).
- Откат — `delete_file`: удаляется только созданный файл.
- Пустой план или пустая стратегия не выгружаются («выгружать нечего»), в журнал ничего не пишется — как у проверок без изменений.
- Библиотека — `fpdf2` (добавлена в `requirements.txt`); reportlab остаётся только фолбэком для старого экспорта ТЗ.
- Шрифт ищется в `FONT_CANDIDATES`; первым идёт `assets/DejaVuSans.ttf` проекта. Нет шрифта — сообщение, а не PDF с квадратами.
- Раздел называется «Планы и схемы», но схемы не рисует: выгружает ровно то, что уже есть в данных. Рисовать диаграммы из плана — отдельная задача, своих данных у неё нет.

### 5.11 Материалы (шаг 6в)

Пять папок фиксированы кодом (буфер, документы, референсы, шаблоны, архив) — это структура проекта,
а не пользовательские папки. Файлы лежат в `<проект>/materials/<папка>/`; в `other_files` добавлена
колонка `path` (для старых баз — `_ensure_columns`), а `id` теперь отдаётся наружу вместе с записью.

- `import_materials(paths, folder)`: копирует файлы в папку проекта (имя не затирается — `_1`, `_2`),
  добавляет записи с типом по расширению, размером, датой и пустыми тегами; откат — `restore_sections`
  возвращает список и удаляет скопированные файлы, исходники пользователя не трогаются.
- `delete_material(item_id)`: убирает только запись, файл остаётся на диске; откат возвращает запись.
  Карантина, как у медиа, здесь нет: материал — это документ, а перемещать чужие файлы без спроса нельзя.
- Раздел в навигации переименован в «Материалы» (был «Прочие материалы»): загрузка через диалог,
  поиск по имени и тегам, фильтр по типу, открытие системным просмотрщиком, предпросмотр изображений
  и удаление записи. Все изменения — через ядро, журнал и откат общие.

### 5.12 Видео (шаг C1)

Готовый `video_processor.py` подключён к ядру: `get_video_info` (ffprobe) и `export_for_platform` (ffmpeg).

- Инструмент `process_video(media_ids, platform)`: площадки из `PLATFORM_SETTINGS` — Reels 9:16, пост 1:1,
  TikTok, Shorts, YouTube 16:9. Готовый файл — `<имя исходника>_<reels|post|tiktok|shorts|youtube>.mp4`
  в `media/images`, при повторе перезаписывается (как `<имя>_web` у фото).
- Исходник ищется по `source_path` → `path` → файл с тем же именем в `media/images`, только среди видео-расширений.
- Запись получает `source_path` (исходник), `path` на готовый файл, `size` = фактические `ШxВ` из `get_video_info`,
  `processed` = площадка. Обработка считается от исходника, а не от прошлого готового файла.
- Откат — `restore_sections`: записи возвращаются, созданные файлы удаляются, исходник не трогается.
- Нет ffmpeg (или ffprobe) — честное «нужен ffmpeg» без записи в журнал: файла нет, менять нечего.
- Подгонка кадра — `scale` + `pad` (чёрные поля), без обрезки по центру: обрезка меняет кадр, это отдельное
  решение, а не следствие подключения.
- Кадр-превью видео (шаг 5) остаётся как был: он снимает кадр с записи, а не с готового файла.
- Роутер видео пока не маршрутизирует — из чата нечем выбрать конкретное видео; инструмент вызывается кнопкой
  в «Публикациях». Выбор видео из чата — следующий подшаг, вместе с субтитрами.
- В `get_video_info` `eval(r_frame_rate)` заменён разбором `num/den`: `eval` по выводу ffprobe — исполнение
  внешних данных.

### 5.13 Субтитры (шаг C2)

- `make_subtitles(media_ids, language="ru", burn=True)`: звук → `extract_audio` (wav 16 кГц моно, временный файл в `/tmp`) → `transcribe` → `.srt` в `<проект>/subtitles/<имя>.srt` (UTF-8 BOM — так его ждёт ffmpeg) → при `burn` готовое `<имя>_subs.mp4` в `media/images`.
- Источник — исходник (`source_path` → `path`), как у `process_video`; повтор перезаписывает `.srt` и `_subs.mp4`, а не плодит копии.
- Откат — `restore_sections`: записи возвращаются, созданные `.srt` и `.mp4` удаляются, исходник не трогается.
- `burn=False` — только `.srt`, запись не меняется (откат удаляет файл).
- Whisper — **опциональная** зависимость и в `requirements.txt` не входит (тянет torch): нет его или речь не распозналась — отчёт «нужен Whisper» без записи в журнал. Облачное распознавание не включаем автоматически: расход бюджета должен быть решением пользователя, а не следствием кнопки.
- VRAM 8 ГБ: Whisper и локальная LLM вместе не живут. В C2 модель не выгружается автоматически (это Ollama `keep_alive`), но риск записан и проверяется на машине пользователя.
- Язык — `ru` по умолчанию; KZ-распознавание остаётся облачным сценарием и в C2 не включается.
- В базу добавлена колонка `media.source_path` (для старых баз — `_ensure_columns`): без неё после перезапуска субтитры и повторная обработка считались бы с уже сжатого `_reels`/`_web` файла.
- Повторная обработка видео считается от имени без суффикса площадки (`_video_stem`): запись без `source_path`, указывающая на `clip_reels.mp4`, даёт `clip_reels.mp4`, а не `clip_reels_reels.mp4`.

### 5.14 Вид для видео (шаг C3)

- В `media` добавлена колонка `processed` (JSON-список): инструменты пишут туда, что сделали (`process_video` — площадку, `make_subtitles` — `subtitles`). Без хранения статус терялся после перезапуска, и «до/после» нечего было бы показать.
- Подписи — `PROCESSED_LABELS` в «Публикациях»: `🎬 Reels`, `🎬 Post`, `🎬 TikTok`, `🎬 Shorts`, `🎬 YouTube`, `💬 Субтитры`. Карточка в медиатеке и панель просмотра показывают их рядом со статусом.
- «До / после» — отдельный `VideoCompareDialog`: два кадра (исходник и готовое), имя файла, размер и длительность. Кадры берутся тем же `_pixmap_for`, что и у фото; длительность — через `get_video_info` (ffprobe), без ffmpeg — «длительность неизвестна», а не выдуманное число.
- Кнопка «🎬 До / после (видео)» стоит в просмотре рядом с «Сравнить с исходником»: фото-диалог сравнивает пиксели кадра, видео нужен кадр плюс длительность. Нет `source_path` — сообщение, как у фото.
- Сравнение только читает: ни файлов, ни базы не меняет, отката не требует.

### 5.15 Файлы из чата для видео и субтитров (шаг C4)

- Накопление статусов: `processed` только дописывается (`_remember`) — повторная подготовка под ту же площадку и субтитры после видео не стирают предыдущие отметки и не плодят дубли. Фото — исключение: `batch_photo` пишет последний рецепт (`crop`/`color`/`compress`), это не история, а что именно сделано с файлом.
- `process_video` и `make_subtitles` принимают `paths` — пути из текста чата. Путь разрешается в запись по `path`/`source_path`; файл не из проекта копируется в `media/images` (`_add_media_record`), оригинал остаётся в `source_path`, поэтому тот же путь второй раз не создаёт копию.
- Копирование — до обработки, но только после проверки ffmpeg: без него файлы в проект не тянутся.
- Откат после обработки по пути: возвращаются записи, удаляются готовые файлы; импортированная копия исходника остаётся в медиатеке (это исходник, а не результат).
- Маршрут из чата: правило срабатывает только если в тексте есть и слово площадки/субтитров, и путь к видеофайлу (`*.mp4|mov|mkv|avi|webm|m4v`). Нет пути — уточняющий вопрос, а не запуск по пустому списку: инструмент из чата без файла не угадывает материал.
- В «Публикациях» те же кнопки работают без выделения: если видео не выбрано, открывается выбор файла на диске, и запуск идёт через `paths`.
- id записей из чата — та же схема, что у импорта; никаких новых таблиц не нужно.

### 5.16 Пакет под Instagram (шаг C5)

- Прямая публикация через Graph API сейчас невозможна: Instagram забирает медиа по публичному URL, а приложение local-first таких URL не отдаёт; нужны ещё бизнес-аккаунт и токен. Поэтому C5 — пакет для ручной загрузки, а постинг остаётся отдельным шагом D («Graph API + публичный хостинг медиа», раздел 4).
- `instagram_pack(dest="")` собирает `<папка>/ГГГГММДД-ЧЧММСС/`:
  - `media/` — копии одобренных материалов (`status = approved`), имя `<дата>_<слаг>.<ext>`;
  - `captions.txt` — дата, тема, подпись и хэштеги по позициям плана;
  - `manifest.csv` — файл; тип; формат; размер; операции из `processed`;
  - `problems.txt` — чего не хватает: нет файла, нет подписи, нет хэштегов.
- Замечания не блокируют сборку: неполный пакет тоже нужен, а `problems.txt` говорит, что дописать.
- Без `dest` — `<проект>/instagram/…`, с `dest` — подпапка в выбранной папке; откат `delete_folder` удаляет только созданную подпапку.
- Копируются файлы, а не ссылки: загрузка с телефона или из веба требует файлов; исходники не меняются.
- Подпись привязана к файлу (`_pair_captions`): сначала позиция плана с тем же `media_id`, затем совпадение дат, затем остатки — в порядке плана. Каждая пара попадает в `captions/<имя файла>.txt`, блок в `captions.txt` начинается с `=== <имя файла> ===`, а в `manifest.csv` есть колонка «подпись» (да/нет). Несвязанные позиции и файлы — в `problems.txt`, а не отдельным списком без якорей.
- Кнопка «📸 Пакет в Instagram» в шапке «Публикаций»; правило чата — «пакет/публикация» + «инстаграм».
- Подписи операций в карточке: `crop`/`color`/`compress` — «Кадр»/«Цвет»/«Сжатие»; незнакомые ключи в интерфейсе не показываются сырым текстом (`_processed_marks`).
- Хостинг медиа для реальной публикации — открытый вопрос (5.17): пока его нет, Graph API не подключаем.

### 5.17 Открытые вопросы

- **Публичный хостинг медиа для Graph API (шаг D, D1 закрывает):** Instagram сам забирает медиа по URL и требует, чтобы сервер был публично доступен в момент попытки публикации. Выбран хостинг — 5.18; если он окажется неудобным, меняется только D2, остальной шаг не зависит от выбора.
- **App Review и Advanced Access:** разрешения `instagram_business_basic` и `instagram_business_content_publish` (или `instagram_basic` + `instagram_content_publish`) требуют заявки на проверку. Без Advanced Access работает только доступ разработчиков приложения. Это действие пользователя в кабинете Meta, кодом его не закрыть.

### 5.18 Публикация в Instagram через Graph API (шаг D, D1)

Факты из документации Meta (раздел «Content Publishing»):
- Meta скачивает медиа сама (`We cURL media used in publishing attempts`), поэтому файл должен лежать на **публично доступном сервере с HTTPS без авторизации** в момент публикации.
- Публикуется только **профессиональный аккаунт** (Business или Creator). Путь «Instagram API with Instagram Login» (хост `graph.instagram.com`, Business Login for Instagram) не требует связанной Facebook Page; путь «с Facebook Login» требует Page.
- Лимиты: контейнер живёт **24 часа**, за 24 часа — не более **400 контейнеров** и **50 публикаций** на аккаунт; если подключённая Page требует Page Publishing Authorization (PPA), публикация падает без её завершения.

Решение:
- **Хостинг — Cloudinary (основной).** Бесплатный тариф без карты, загрузка одним POST на `api.cloudinary.com/v1_1/<cloud>/image/upload` (без SDK, только `requests`), отдача — `res.cloudinary.com/<cloud>/image/upload/…` без логина. Buffer и официальные туториалы рекомендуют именно его для этого кейса: прямой URL получается сразу после загрузки. Удаление — тем же API с подписью, поэтому откат D2 возможен.
  - Резерв — Cloudflare R2: бесплатные 10 ГБ и нулевой исходящий трафик, но публичный доступ требует отдельной настройки (публичный бакет или свой домен), а загрузка идёт по S3-протоколу. Переход не меняет D3/D4.
  - Не подходят: GitHub Pages (запрещено для бизнеса, 1 ГБ на сайт), Vercel Hobby (только некоммерческое использование), анонимные файлообменники (нет гарантий срока жизни и удаления — а откат нужен).
- **Токен — долгоживущий токен пользователя Instagram** (не Page-токен и не короткий на час). Хранится **не** в `settings.json` и **не** в базе проекта: отдельная таблица в общей `data/app.db`, значение **шифруется** (согласно таблице стека, раздел 3). Ключ шифрования — вне репозитория (переменная окружения или системное хранилище ОС). В интерфейсе показываются только последние 4 символа; токен не попадает в журнал, логи и `actions_log`.
  - Доступ разработчика в приложении Meta нужен для проверки; Advanced Access запрашивается отдельно (см. 5.17).
- **Проверка бизнес-аккаунта (D3, read-only, без публикации):**
  1. `GET /me?fields=id,username,account_type&access_token=…` — аккаунт отвечает, `account_type` равен `BUSINESS` или `CREATOR`;
  2. проверка, что токен живёт (ошибка `OAuthException` с кодом 190 означает протухший или отозванный токен);
  3. права `instagram_business_basic`/`instagram_business_content_publish` видны в ответе Graph API Explorer или по попытке одного read-only запроса с ними.
  По этим трём пунктам D3 считает доступ готовым; PPA проверяется вручную в Meta Business Suite, если публикация упадёт с соответствующей ошибкой.
- **Публикация (D4):** только после D2+D3, с обязательным подтверждением (правило ядра), dry-run по умолчанию; каждый вызов пишется в журнал, откат удаляет загруженный файл и помечает публикацию как отменённую локально (саму опубликованную запись из Instagram приложение не удаляет — это ограничение API).

Открытые вопросы, которые остаются после D1:
- Действительно ли Cloudinary отдаёт наши видео без трансформации и не режет качество — проверяется на D2 живым файлом.
- Сколько живёт долгоживущий токен на практике и как часто его обновлять — измеряется на D3.
